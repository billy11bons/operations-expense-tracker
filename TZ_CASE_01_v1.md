Версия 1 от 07.09.2026. Этап 1: рабочее ТЗ учебного MVP. Разработка ещё не начата.

## 1. Исходная задача

- Площадка: Upwork.
- Название: I need someone to set up automated operations & expense tracker.
- URL: https://www.upwork.com/freelance-jobs/apply/need-someone-set-automated-operations-expense-tracker_~022092046407629084004/
- Бюджет: $8–15/hour, почасовая ставка, а не фиксированная стоимость проекта.
- Ниша: Operations + expense tracker / Google Sheets, малый бизнес.
- Задача: привести в порядок существующую таблицу и превратить её в ежедневный трекер расходов и рабочих задач с автоматическими недельными итогами и отметкой Pending.

Источники: неизменяемый `../Tracker_Codex_TZ/01_operations_expense_tracker_codex.md`; `../Tracker_Orders_Database.xlsx`, лист «Сводная база», A2:N2, также строки №1 листов «Для рабочей тетради», «ТЗ для Codex» и «Источники»; секция «Кейс №1» исходной DOCX-тетради, поля исходного заказа и Шага 1. Дата проверки объявления 06.09.2026 взята из базы; актуальность объявления и ставки онлайн на этом этапе не проверялась.

Разделяем реальную задачу и учебную адаптацию: клиентская задача связана с существующей Google-таблицей. Исходное учебное ТЗ разрешает responsive web MVP с локальным хранением. Исходная таблица клиента не предоставлена. Поэтому очистка и миграция её фактических данных не считаются выполненными и не входят в текущую приёмку. Совместимость, импорт и синхронизация Google Sheets не обещаются.

## 2. Цель продукта

Позволить владельцу малого бизнеса ежедневно фиксировать расходы и рабочие задачи, видеть сумму расходов текущей недели и задачи, требующие внимания, без ручного пересчёта.

## 3. Пользователь / роли

Допущение для MVP (D1): один оператор — владелец или администратор бизнеса, имеющий полный доступ к записям. Авторизации и разграничения прав нет. Owner — текстовое имя ответственного за задачу, а не учётная запись. Одновременная работа нескольких пользователей не поддерживается.

## 4. Основные сущности

Поля расходов и задач взяты из исходного ТЗ. Типы, обязательность, значения по умолчанию и ограничения ниже — Допущение для MVP (D2).

| Сущность | Данные |
|---|---|
| Expense | id: уникальная строка; date: обязательная дата YYYY-MM-DD; categoryId: обязательная ссылка на категорию; description: обязательный непустой текст до 200 символов; amountMinor: положительное целое число центов; paymentMethod: обязательное Cash/Card/Bank transfer/Other; note: необязательный текст до 1000 символов |
| Task | id: уникальная строка; task: обязательный непустой текст до 200 символов; owner: необязательный текст до 100 символов; dueDate: обязательная дата YYYY-MM-DD; status: New/In Progress/Pending/Done, по умолчанию New; priority: Low/Medium/High, по умолчанию Medium; note: необязательный текст до 1000 символов |
| Category | id: уникальная строка; name: уникальное после обрезки пробелов и без учёта регистра название, 1–50 символов |

Сумма вводится в денежных единицах с максимум двумя десятичными знаками, допускается точка или запятая без разделителей тысяч. Диапазон 0.01–999999999.99; отрицательные значения, ноль, NaN, бесконечность и лишние знаки после разделителя отклоняются. Преобразование в центы должно сохранять десятичное значение точно. Сумма в центах и итог должны оставаться безопасными целыми числами JavaScript; переполнение отклоняется с сообщением.

Категории по умолчанию: Supplies, Transport, Utilities, Other. Отдельные сущности сотрудников, проектов и платежей не нужны.

## 5. Основные экраны

1. Dashboard: четыре карточки — расходы текущей недели, Pending, overdue, Done; явный диапазон недели и валюта.
2. Expenses: список, создание/редактирование через форму, удаление с подтверждением, фильтры периода и категории.
3. Tasks: список, создание/редактирование через форму, удаление с подтверждением, изменение статуса, фильтры статуса и приоритета; отдельные признаки Pending и overdue.
4. Settings / Categories: список категорий и добавление категории.

Допущение для MVP (D3): минимальное управление категориями ограничено просмотром и добавлением; переименование/удаление категорий не требуется. Это сохраняет ссылки существующих расходов. Дополнительные настройки валюты, пользователей и отчётов отсутствуют.

## 6. Функциональные требования

- F1. Создание, чтение, изменение и удаление расходов со всеми полями из раздела 4.
- F2. Создание, чтение, изменение и удаление задач; изменение статуса без потери остальных полей.
- F3. Автоматическое обновление недельной суммы и карточек после соответствующих изменений, без перезагрузки страницы.
- F4. Отметки Pending и overdue, включая одновременное отображение обоих признаков у одной задачи.
- F5. Фильтрация расходов по дате от/до включительно и категории, задач — по статусу и приоритету; комбинация фильтров через AND, сброс к полному списку.
- F6. Сохранение расходов, задач и категорий после reload.
- F7. Демоданные при первом открытии: расходы внутри/вне текущей недели и задачи с разными статусами/сроками. Использовать даты относительно дня инициализации.
- F8. Минимальные категории по разделу 5; добавленная категория доступна в форме и фильтре расходов.
- F9. Удобная навигация по четырём экранам, формы с понятной валидацией, usable mobile/desktop.

Допущение для MVP (D4): сортировка расходов по дате убыванию, задач по сроку возрастанию, при равенстве — по id. Фильтры влияют только на списки, карточки Dashboard всегда рассчитываются по всем данным. Фильтры не сохраняются после reload. Если начало периода позже конца, показать ошибку и не применять некорректный фильтр.

## 7. Бизнес-логика

Допущение для MVP (D5): одна валюта USD, без пересчёта курсов, налогов, доходов и возвратов. Выбор USD сделан только для учебной демонстрации; валюта реального бизнеса неизвестна.

Допущение для MVP (D6): неделя начинается в понедельник и заканчивается в воскресенье включительно. «Сегодня» определяется по локальному календарю браузера. Даты расходов и сроков хранятся как календарные строки, без UTC-конвертации. Даты в будущем разрешены; сумма определяется датой расхода, а не датой создания записи.

- Weekly total = сумма amountMinor записей с date от понедельника текущей недели включительно до следующего понедельника исключительно; вывод с двумя десятичными знаками и USD. Пустая выборка = 0.00 USD.
- Pending = количество задач со status = Pending независимо от срока.
- Overdue = количество задач с dueDate < сегодня и status != Done. Срок сегодня ещё не просрочен.
- Completed = количество задач со status = Done за всё время; недельное ограничение не применяется.
- Pending может одновременно быть overdue; карточки не являются взаимоисключающими частями общего количества задач.
- Done никогда не overdue; возврат Done в другой статус повторно рассчитывает просрочку.
- Разрешены переходы между любыми четырьмя статусами без согласования или истории переходов (Допущение для MVP D2).
- Пересчитывать календарные показатели при открытии, изменениях данных, возвращении фокуса и наступлении следующего локального дня, если приложение остаётся открытым (Допущение для MVP D6).

## 8. Хранение данных

Допущение для MVP (D7): localStorage, один документ с schemaVersion = 1, expenses, tasks, categories и признаком инициализации; ключ `case01.operationsExpenseTracker.v1`. Чтение только в браузере после готовности клиентской части.

Демоданные записываются лишь при отсутствии ключа, никогда поверх сохранённых данных. Пустые массивы после удаления всех записей — корректное сохранённое состояние. При ошибке чтения/неверной структуре показать сообщение, не перезаписывать содержимое автоматически. При ошибке записи не показывать успешное сохранение и не заменять предыдущее подтверждённое состояние. Ввод формы сохраняется для повторной попытки.

Хранение привязано к браузеру, профилю и origin (включая порт); очистка данных браузера удалит записи. Облачной синхронизации, резервного копирования и поддержки одновременного редактирования в нескольких вкладках нет.

## 9. UI/UX требования

Адаптивные списки/таблицы и формы, читаемые суммы и даты, видимые подписи обязательных полей и ошибки рядом с ними. Pending и overdue различаются текстом и цветом; нельзя полагаться только на цвет. Удаление требует подтверждения, отмена не меняет данные. Пустой список объясняет отсутствие данных или совпадений фильтра.

Допущение для MVP (D8): интерфейс на английском, как названия областей исходного brief; документация на русском. Удобство проверяется на ширинах 390 и 1440 px: без горизонтального скролла всей страницы и перекрытий элементов; длинные списки допускают вертикальный скролл. Доступ к формам с клавиатуры, видимый focus, кнопки с понятными названиями. Финальная стилизация выполняется на отдельном согласованном этапе.

## 10. Что входит в MVP

F1–F9, четыре экрана, модель данных, правила вычислений и сохранения, демоданные, базовая адаптивность. При последующих разрешённых этапах: README с локальным запуском и ограничениями, проверка CRUD/расчётов/фильтров/сохранения, отчёты о фактических результатах. На этапе 1 создаются только ТЗ, журнал и текст тетради.

## 11. Что НЕ входит в MVP

Авторизация, несколько пользователей/организаций, cloud sync, Google Sheets API, очистка/импорт реальной таблицы без её получения, AI, внешние API, платежи, сложная аналитика, отчёты кроме четырёх карточек, экспорт, уведомления, вложения, повторяющиеся задачи, канбан, бюджетирование, валютные курсы. Публикация требует отдельного разрешения пользователя в соответствующем этапе.

## 13. Допущения

Все решения D1–D8 — «Допущение для MVP», не подтверждённые требования клиента:

- D1: один оператор, без login, owner текстом.
- D2: обязательность и валидация полей, четыре статуса, три приоритета, фиксированные способы оплаты, свободные переходы статусов.
- D3: стартовые категории и только их добавление/просмотр.
- D4: правила фильтров, сортировки и независимость Dashboard от фильтров.
- D5: USD, только положительные расходы, без налогов и конвертации.
- D6: понедельник–воскресенье, локальный календарь, правила overdue и обновления даты.
- D7: localStorage, один браузер, однократная инициализация demo.
- D8: английский UI, русский комплект документов, проверочные ширины 390/1440 px.

Учебная веб-адаптация разрешена исходным brief, но не заменяет согласование формата поставки с реальным клиентом. Ответы клиента могут потребовать новой версии ТЗ до разработки соответствующих изменений.

## 15. Рекомендуемый технический стек

Следуем рекомендации исходного ТЗ: Next.js + TypeScript + Tailwind CSS, localStorage. Серверная БД для этого учебного объёма не нужна. Четыре маршрута: `/`, `/expenses`, `/tasks`, `/settings`; вычисления и сохранение выделяются из UI, чтобы отдельно проверить календарь и денежные суммы.

Конкретные совместимые версии, установка зависимостей и проверка команд запуска относятся к этапу 2. На этапе 1 пакеты не устанавливаются. Весь будущий код — только `app/` внутри папки кейса. Никаких внешних сервисов для работы MVP не требуется.
